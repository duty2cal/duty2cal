# 1. Introduction and Goals

## Requirements overview

`duty2cal` (the deliverable of the change to export released roster calendars) is a local, offline converter with two realizations of one conversion contract. A crew member supplies one Lufthansa cabin-crew duty-plan PDF published as a Jeppesen PDF export — the one plan the project names and converts; the executable writes one complete RFC 5545 calendar beside it under an unused name, or fails explicitly and attempts a numbered diagnostic. The browser conversion page, served from the built Site output, performs the same conversion inside the tab, offers `<source-stem>.ics` for the browser to save, and writes nothing. Neither realization overwrites an existing calendar or report.

The browser conversion page is published as the **Public website** at `https://duty2cal.github.io/`: a Site publication builds the Site output from a named Built revision, gates it on the page-content, licensing, browser and conversion evidence, replaces the hosting target's content as a whole, and the page's footer names and links the revision it was built from. The hosting target holds only built output and is never edited by hand, and a release publishes its archive only after the Site publication for its tag succeeded.

Top requirements, from the stakeholder perspective:

1. **Faithful conversion** — every required activity in the supported plan — a Lufthansa cabin-crew duty plan published as a Jeppesen PDF export — is represented, with correct all-day/timed distinction and correct UTC endpoints; nothing is silently omitted.
2. **Complete-or-explicit-failure** — a plan that cannot be represented completely is rejected with a visible failure and a diagnostic, never a partial calendar.
3. **No destruction** — an existing calendar or report is never replaced; new outputs use an unused enumerated name.
4. **Privacy** — private duty plans and identifying values never reach the public repository; fixtures and golden calendars are generated or anonymized.
5. **Reproducible public home** — the organization's settings, its repositories, the protection rules for the default branch and for the pages repository, the published site's source, the repository's security settings, the pages publishing credential, and the organization profile content with its default security policy are declared in the repository; the objects that already exist on GitHub are bound to their declared counterparts without being created, modified or deleted; and a reviewed configuration change previews every difference, applies it, and records the values it applied, so the public home can be reviewed, diffed and rebuilt instead of remembered. A declared object the live configuration lacks — the organization profile repository and its files, the pages deploy key and its secret, and the pages rule set — is created by the apply, and the credential's private half lives only in the encrypted applied state; the two facts the mechanism cannot express, the pinned repositories and private vulnerability reporting, are recorded manual steps.
6. **Distributable release** — one self-contained Windows x86_64 executable, published from one public repository as a verifiable, immutable release whose notes state the changes a user receives, including dependency updates, drawn from the change log the repository keeps, licensed MPL-2.0 project-wide (weak file-level copyleft; App-Store distributable), with claims backed by evidence. Windows x86_64 is the only supported platform in the sense of a published archive: no other archive is published and none is tested by the project's automation, builds for other operating systems are available on request, and other platforms' source can be built with a Rust toolchain. The browser conversion route is a supported conversion route, not an archive platform.

The authoritative behaviour specification lives in the merged corpus `givn/specs/export-duty-plan-calendar/`; the change to export released roster calendars holds the historical home of that delta at `givn/archive/export-released-roster-calendar/specs/`.

## Quality goals

| Priority | Quality attribute | Motivation |
|---|---|---|
| 1 | Correctness / completeness | A calendar that looks complete but omits or invents activities is worse than an explicit failure; the whole-plan completeness boundary enforces this. |
| 2 | Reliability (no data loss) | Existing calendars and reports must survive any conversion attempt, including concurrent ones. |
| 3 | Interoperability | The output must be a valid RFC 5545 file (CRLF, escaping, octet-aware folding) usable by real calendar clients. |
| 4 | Privacy | Duty plans carry identifying data; public artifacts must contain only generated or anonymized material. |
| 5 | Maintainability / portability | Clean Architecture layering plus one self-contained Windows x86_64 executable keep the converter verifiable and distributable. |
| 6 | Reproducibility of the public home | The public home's configuration must be reviewable, diffable and rebuildable from the repository, and the one-time adoption of objects that already exist must change nothing live; a later configuration change then applies the declared values — including the repository's security settings, the pages publishing credential and the pages protection rule set — and records what it applied, while a refusal changes nothing and a partial failure names the object that failed. A record that can only be remembered in the web interface is the failure this goal prevents; so is a publishing key generated by hand. |
| 7 | Release integrity / verifiability | A released version offers exactly one Windows x86_64 archive, byte-reproducible, checksummed, carrying build provenance and a bill of materials, and published immutably, so a downloader can trace the file in hand to the released revision and no published promise outruns its evidence. The release also states what changed: its notes are the newest section of the repository's change log, grouping the changes a user receives — capability changes and dependency updates — and refusing a version that would name none. |
| 8 | Truthful public copy | The organization profile states only what the repository keeps: the converter and the one plan it converts — a Lufthansa cabin-crew duty plan published as a Jeppesen PDF export, with the boundary that cockpit duties, other Lufthansa duty plans, other Jeppesen exports and another operator are not covered — the browser conversion route now reachable on the Public website at `https://duty2cal.github.io/`, Windows x86_64 as the only published archive platform with builds for other operating systems available on request, no hosted converter or upload, and an explicit non-affiliation sentence naming Lufthansa and Jeppesen. One support statement is carried by the website, the README, the organization profile, chapter 3 and both issue forms; a check refuses a carrier that disagrees. It names the same guarantees for both conversion realizations. It links the stable latest-release address, the source and the site repositories, attributes the third-party Unicode data to Unicode-3.0, embeds no third-party image or widget, and links only absolute addresses, so reading the page contacts no other service. The published page carries its own statements, so a reader who lands on the site never has to take the profile's word for it: above the file picker it states what the tool does, the browser route, downloads for various operating systems available on request with its release page linked, the privacy rule, the non-affiliation sentence and the as-is sentence; below the converter it carries the source and the licence; and its footer names the Built revision. It does not prescribe a Windows download, because the one-archive platform rule is the release channel's claim, not the page's. |

## Stakeholders

| Role | Expectation |
|---|---|
| Crew member exporting their own duty plan (`crew-member--personal-calendar-owner`) | A usable personal calendar that faithfully represents their plan, with clear failures and no invented dates — and, on Windows x86_64, a downloadable executable that runs without installation, together with release notes that state what changed since the version they have. On any platform with a current browser, the same conversion runs in the tab on the Public website at `https://duty2cal.github.io/`, with the plan never leaving the page and the footer naming the revision that built it. A crew member on any other platform without a browser route reads that no archive is published, that builds for their platform are available on request, and that the source can be built with a Rust toolchain. A prospective user also reads a public organization profile that tells the truth about the current release and links the download and the source. |
| Person identified in a duty plan (including its owner) | Their identifying information never enters the public repository or public test material. |
| Maintainer responsible for a public release (`project-maintainer--release-owner`) | A maintainable, verifiable, legally distributable converter whose public support claims match its evidence, and a public home whose release channel serves one verifiable, immutable Windows x86_64 archive per version and states, in the repository's change log, what each version changed. The Public website serves the same release: the maintainer publishes the page from a named revision, its footer names that revision, a site failure blocks the release, and no public copy promises a page that is absent. |
| Organization owner (`project-maintainer--organization-owner`) | A public home whose organization settings, its repositories, default-branch protection, site source, pages publishing credential and profile content are declared in the repository and bound to what already exists or created by a reviewed apply, so an administration change can be reviewed and diffed before it reaches GitHub and the one-time adoption changes nothing live; holds the administration authority, the token and the state passphrase, which is now also the only recoverable copy of the pages publishing key, and performs the one-time pinned-repository step by hand. |
| Contributor reviewer (`contributor--infrastructure-reviewer`) | Can read the declaration, the adoption batch, the reviewed profile and security-policy text, and the encrypted applied state in the same history as the code, review an infrastructure change beside the workflow or document it supports, and confirm the state is ciphertext; holds no token or passphrase and cannot apply. The confirmed build-configuration reviewer (`contributor--build-configuration-reviewer`) is a segment of the same stakeholder type: they judge whether a size attribution is reproducible and names the right artifact, and what a build-configuration change costs a crew member. The confirmed web reviewer (`contributor--web-reviewer`) is a third segment: they read the page, the script, the WASM bundle and the Site publication in the same history, judge the Content-Security-Policy and its browser evidence, and confirm that every published statement matches the built output; they hold no publishing authority, no deploy key and no passphrase, and cannot weaken the no-network claim. |
