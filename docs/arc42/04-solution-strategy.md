# 4. Solution Strategy

## Key decisions

- **A pure core behind ports.** `duty2cal-core` holds the domain, the application ports and the dependency-free ICS adapter; `duty2cal-pdf` owns the extraction of the frozen supported subset and only the file-structure layer stays third-party; `apps/cli` wires them. The compiler, `cargo deny`+clippy, archunit tests and review conventions enforce the inward-only rule (ADR-0002); ADR-0008 fixes the shipped extractor boundary.
- **Staged pipeline with a completeness gate and row diagnostics.** Source recognition → classification → endpoint date resolution → description composition → calendar composition → publication. Every detail row is processed in one pass and every finding is collected: a row that cannot be represented is a conversion error, a row represented from printed evidence without a recognized activity code is a conversion warning. The `Roster` aggregate reaches "complete" only when no conversion error remains; publication happens after that gate, so a partial calendar can never be published, while a calendar with warnings is published together with its warning report.
- **Determinism scoped to the source snapshot.** Component identity derives from the source snapshot plus the represented activity, not from an output counter or a title (opaque discriminator; the readable date/flight/route recipe was rejected as non-unique).
- **Create-new publication.** New calendars and both report kinds are written only to an unused name (create-new semantics with retry); existing or concurrently claimed files are never replaced.
- **Explicit failure as a first-class outcome**: the CLI names the source and the reason in a numbered failure report written beside it and reports the failure through its exit status; the use case returns a typed error rather than a partial calendar. A conversion with warnings exits successfully, prints each warning, and writes a numbered warning report. Unevaluated rows never hide behind the first error: the failure report carries every error and warning of the run.
- **Browser-local delivery channel (ADR-0007).** A second driving adapter, `ffi/wasm` (`duty2cal-wasm`), wraps the unchanged application boundary for `wasm32-unknown-unknown`, and a static `web/` page runs it inside the tab. The WASM bytes are inlined as base64 so the page can keep `connect-src 'none'` and load no third-party asset. The page owns the offer: it creates a Blob and an `<a download>`, writes nothing, and never claims a save; the browser owns the save location and any collision. It lists the unknown duties beside the calendar in its ready state, lists the warnings and errors of a failure, and offers the matching report, so a reader never has to open a file to understand a run. The page has no backend, no upload, no persistent storage and no navigable state. The browser is a supported conversion route but not a published archive platform: "supported platform" stays Windows x86_64 in the archive sense.
- **Published page from one gated command.** The Public website is not hand-published and not edited in the hosting target. One project-owned command decides whether the revision is a site input (`--since` compared against the path list it owns), checks the revision out into a detached worktree, builds the Site output (`dist/site/`) there, stamps the footer with `git describe` output linked to the commit, runs the page-content, licensing, browser and conversion checks as real subprocesses inside that worktree, and replaces the target's content with one fast-forward commit. The target accepts only a write-enabled deploy key (ADR-0006's state holds its private half) and admits no force push, so whole-content replacement is an ordinary commit and every earlier page stays in the target's history. A revision that changes none of the site's inputs publishes nothing; republishing a revision the target already holds reports the target as current and writes nothing; every release tag republishes the page from the tagged revision, and a release publishes its archive only after that publication succeeded and the target's branch tip carries the tagged Built revision. After the replacement the command fetches the published address (`--verify-url`) with bounded retries and refuses unless the served page names the same Built revision, so a push the host does not serve is never reported as a publication. One reusable workflow (`site.yml`) is the only host-side implementation, called by `web.yml` for default-branch pushes and manual dispatch and by the release's `site` job for a tag. The same command runs on a workstation against a local git target, which is how the path is tested without GitHub. The page carries one mark in two forms: the vector master (`docs/assets/duty2cal.svg`) is the header mark and the tab's primary icon, and the raster (`docs/assets/duty2cal.png`) stays as the tab alternate for a browser without SVG tab icons; both are same-origin members of the output, and the content check refuses a page that swaps the header mark for the raster or drops the alternate.
- **Infrastructure as code for the public home.** The organization, both repositories, the default branch's existing rule set, the Pages source, the monorepo's security settings (secret scanning, push protection and the two Dependabot settings) and the pages publishing plumbing (the deploy key, its secret and the pages rule set) are declared under `infra/` with OpenTofu and the GitHub provider (ADR-0005). The objects that already exist are bound once by a read-only adoption into an encrypted local state that is committed (ADR-0006), so a later preview can compare the declaration with what GitHub holds; a configuration change then applies exactly the previewed revision from the maintainer's workstation and the resulting state is committed only after a green apply. Objects the declaration adds and live lacks — the profile repository and its files, the publishing key and its secret, the pages rule set — are created by the apply behind a read-only creation guard, and the key pair is generated inside the declaration so its private half exists only in that encrypted state. No apply runs in Actions, because the administer token must not live in the repository it administers.
- **Release strategy.** The one supported archive platform, Windows x86_64, is cross-built on Linux and its executable is started on Windows before publication, so the archive is built where the project's toolchain lives and started where it must run. Packaging happens once on Linux: `scripts/prepare-release.sh` turns the one already-built Windows executable into one deterministic `.tar.gz` archive and checksum plus the release text, and refuses a set that is missing that executable or contains one for a platform outside the supported set. A crew member on any other platform obtains a build on request or builds the source with a Rust toolchain; no archive is published for it. The release text is the newest section of the change log the repository keeps — rendered from the same history, grouped by kind and filtered to the changes a user receives (a revision whose change touched none of the paths a user's copy is made of is left out, and a dependency update that changed the dependency graph is announced under Dependencies), and drift-checked against the released revision — so the page and the repository cannot disagree. The release is published draft-first and immutably from the public repository, with build provenance and a bill of materials attached to every archive, and the published release is then read back and its checksums and attestations verified (ADR-0003; the draft-first immutable publication is ADR-0004).

| Executable specification | Gherkin `.feature` files run by cucumber-rs (strict) | Chapter 2. |

| Browser bundle and page | `wasm-pack --target web`, a base64 inline module, hand-written HTML/CSS/ES modules, no framework or bundler | ADR-0007; chapter 8. |

| Published site | One project-owned command: assemble `dist/site/` from the page, the two legal notice pages, the vector mark and its raster tab alternate, the script, the capability gate, the stylesheet, the two bundle members and the licence, gate it (page content, licensing, browser, conversion), report the target as current when it already holds the output, replace the hosting target's content in one fast-forward commit, then verify the served page names the Built revision; `git describe` stamps the footer at build time; a local bare git repository is the test twin | Chapter 2; `design.md`; chapter 7. |
| Release coupling | The release has a `site` job that calls the reusable site workflow for the tagged revision, then a `publish` job (`needs: site`) whose command verifies the hosting target's branch tip carries the tagged Built revision and only then publishes the draft-then-public release | Chapter 2; `design.md`; chapter 7. |
| Distribution | One self-contained Windows x86_64 executable (cross-built on Linux, started on Windows), published as an immutable release from the public repository; other platforms receive no published archive and obtain a build on request or build from source. | Size attribution | `cargo-bloat` 0.12.1, pinned, run by `scripts/measure_executable_size.py`; the shipped artifact and a second build that retains the names the measurement needs are measured separately and their two numbers are never substituted | Chapter 2; `design.md`. |

| Applied state and drift | Local, passphrase-encrypted state committed under `infra/`; the state is the only copy of the pages publishing private key; the drift check runs on the maintainer's machine | ADR-0006 (amended 2026-10-19); chapter 2. |

ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0005, ADR-0006, ADR-0007 and ADR-0008 are the project's ADRs; the remaining choices are supplied constraints (chapter 2), a local mechanism owned by `design.md`, or product behaviour owned by the capability specification and the glossary. ADR-0007 records the browser-local conversion facade; the browser-owned save and the Playwright driver are owned by the capability specification and `design.md`, not by an ADR. ADR-0008 records the shipped extraction boundary and the frozen supported subset; the word seam, the generated differential corpus and the same-revision measurement commands are owned by `design.md` and the capability specification. The site publication minted no ADR: the choice of an external Pages repository written by automation was already decided in ideation and is recorded as a deployment fact in chapter 7, while the publication mechanism (one command, the assembled output, the build-time stamp, the release ordering) is a local mechanism owned by `design.md` and the behaviour is owned by the two capability specifications.

## Approach to quality goals

| Quality attribute | Approach |
|---|---|
| Correctness / completeness | Whole-plan gate before publication: every detail row is processed, a row that cannot be represented rejects the conversion, and a row represented from printed evidence without a recognized code publishes with a warning; contradictions and unresolved rows still reject it. |
| Reliability (no data loss) | Create-new publication with enumerated retry; numbered preserved reports; existing contents untouched. |
| Interoperability | Hand-written writer with CRLF, escaping and octet-aware folding, asserted on the published file. |
| Privacy | Generated/anonymised fixtures only; no private sources in the repository. The browser page makes no other-origin request after load, loads no third-party asset, and stores nothing persistent. |
| Maintainability / portability | Hexagonal layout with mechanical layer enforcement; one self-contained Windows x86_64 executable; a core free of I/O, clock and environment; the same core and ports behind the WASM facade; an owned extraction for the frozen supported subset with the third-party extractor kept as a test-only oracle (ADR-0008). |
| Browser-local conversion | One facade over the unchanged application; inline WASM under a self-only CSP; a browser-owned save with no page write; capability and startup gates with an explicit message; a real-Chromium `@e2e` scenario plus regular variants. |
| Published public website | One gated publication command; the artifact the gate inspected is the artifact published; whole-content replacement as one fast-forward commit; a build-time Built revision in the footer that the publication refuses to fake; fail-fast named checks; a local git target and a rendered check of the published tree; the release gated on the site deploy. |
| Reproducibility of the public home | One declaration under `infra/` reviewed with the code; a read-only adoption that binds the existing objects and changes nothing live; an encrypted committed state that also holds the generated publishing key; a preview that names every difference; a creation guard for objects live lacks; an apply of exactly the previewed revision whose state is committed only after success; a local drift check. |
| Release integrity / verifiability | One Windows build on Linux plus a start on Windows; a single deterministic packaging step with one archive, its checksum and the release text; draft-first immutable publication with provenance and a bill of materials; a read-back verification job; a measured size attribution of the distributed executable, produced for every pushed revision, with the executable's own file size reported beside the split; a same-revision backend measurement on the Windows executable and the browser bundle against the previous extraction (ADR-0008). |
