# 11. Risks and Technical Debt

## Risks

| ID | Risk | Probability | Impact | Mitigation |
|---|---|---|---|---|
| R-001 | The pinned extraction crate (`pdfplumber = 0.4.1`) exposes different positioned-word/table APIs than expected, so extraction code must be adapted. | Medium | Medium | Build re-proved on rustc 1.98.1; the extraction task adapts to the documented 0.4.1 API before conversion logic is written. |
| R-002 | The Windows GNU cross-build and the executable's absence of companion runtime imports are unproven. | Medium | High | Release-evidence task builds the Windows target and inspects the executable's runtime imports; no release claim without it. |
| R-003 | **Closed**: `./measure-coverage.sh` and `./merge-coverages.sh` exist at the repository root, are wired into `givn/commands.yaml` (`measure_command`, `merge_command`), and measure the whole workspace with `cargo llvm-cov --workspace`, as design.md records. | Low | Low | None open: the scripts run and the merged report feeds the README badges. |
| R-004 | The expert-provided SB/SBX/RE semantics and the qualifier boundary rule are not yet validated against a real dated duty-plan row. | Medium | Medium | Generated fixtures for tests; the local real-source validation obligation is carried; generated layouts are not presented as producer evidence. |
| R-005 | Private data leaks into a public artifact. | Low | High | Generated/anonymised fixtures only; review gate; a calendar-syntax-aware guard replaces the first draft's false-positive PII regex. |
| R-006 | The parked ideation questions reopen: source-derived publication rights (Q5), formal FZ expansion/provenance (Q13). | Low | Low | Both out of scope for this change (generated fixtures; no formal FZ claim). |
| R-007 | MPL-2.0 is file-level copyleft: a redistributor of a modified product must publish the modified MPL files, but nothing protects the rest of a larger proprietary or store-distributed work (ADR-0001 consequence). | Low | Low | Accepted — this is the price of App-Store distribution for the future iOS UI. Revisit only if strong copyleft becomes a requirement, which would need a CLA. |
| R-008 | `archunit` 0.0.2 is pre-1.0 and syntax-based (file granularity, no macro expansion), so some intra-crate layer violations are undetected (ADR-0002 consequence). | Medium | Low | The clippy `disallowed-types`/`disallowed-methods` policy covers I/O/clock/environment; review conventions cover the rest; revisit when archunit stabilises. |
| R-009 | The narrowed release workflow's one Windows cross-build and its one Windows smoke start are provable only on the host, so a broken job or a changed runner image is visible only in a tagged run. | Medium | High | `rhysd/actionlint:1.7.12` covers schema, expressions and known action inputs before the push; `smoke-windows` starts the cross-built `duty2cal.exe` on `windows-latest` and asserts its usage line, non-zero exit and allowed DLL imports; the first tagged run is the remaining host evidence. A failed `build` or `smoke-windows` job leaves no release at all. |
| R-010 | **Closed 2026-10-17**: the macOS archives are unsigned, so a browser download is quarantined and needs a one-time approval. No macOS archive is published after this change, so the risk no longer arises; already-published macOS archives stay as released. | Low | Low | None open for future releases. The published `0.1.0` macOS assets remain immutable and are not re-published. |
| R-011 | The release path's actions and tooling are pinned by mutable tags and branches rather than commit SHAs: `actions/checkout@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8` and `actions/attest@v4` are GitHub's own actions pinned by major tag, while `dtolnay/rust-toolchain@stable` (a rolling branch, used by every build job) and `anchore/sbom-action@v0` are third-party, and `rhysd/actionlint` is a third-party container image pinned by tag on the CI side; a moved tag or branch could inject code into the release path. | Low | High | Accepted deliberately — commit-SHA pinning is the named follow-up, to be adopted repository-wide in one change with Dependabot updating the SHAs. No detection claim is made: release attestations are produced after the release steps run, so a substituted step would be attested as if it were the intended one, and provenance covers a file's origin, not the integrity of the path that built it. |
| R-012 | A published release is immutable, so a botched tag or a broken archive cannot be repaired in place and a used tag is never reusable. The published `0.1.0` archives are the realised instance: CI's artifact transport did not carry the file mode, so they store the executable without the execute bit. | Medium | Medium | Accepted deliberately as the price of a verifiable release (D3): a correction is the next version, never a repair in place. The `0.1.0` archives stay as published; only future releases are Windows-only. The packaging fix (forcing the mode) is in place for later versions. |
| R-013 | The pinned `pdfplumber` is proven only on the Linux test host and the Windows GNU cross-build; the release path no longer compiles any other target. | Medium | Medium | The one build and the `windows-latest` smoke cover the distributed executable, and the preparation refuses a missing or unreadable Windows binary rather than staging quietly. A source build for another platform is outside the evidence the project holds. |
| R-014 | The private-data guard recognises two shapes only: identifier-shaped tokens and complete calendar dates outside the fictional convention. Private material in another shape (a route, a name, a free-text remark) passes it. | Low | High | The guard is a gate for the leak class that actually occurred; the privacy rule (generated or anonymised material only) and review remain the controls for everything else, and the guard's rules are tightened whenever a new leak shape is found — as they were in this change. |
| R-015 | The pinned generator's output shape can move between versions: `git-cliff`'s templates and grouping have changed across releases, and the drift check compares bytes, so a version bump can change the committed change log without any history change. | Low | Medium | Accepted deliberately: the pin and the renderer's version refusal make a mismatch loud rather than silent, and a bump is a deliberate change that re-renders the file, never an automatic one (the `cargo-about` 0.9.0 pin is the same rule). |
| R-016 | The capability allow-list drifts from the corpus: a new capability added under `givn/specs/` without a matching entry in `cliff.toml` would leave its changes out of every release. | Medium | Medium | The renderer compares the allow-list against the use-case ids under `givn/specs/` and refuses on any difference, so the two cannot diverge quietly; the `changelog` job runs it on every push and pull request. |
| R-017 | The notes inherit their quality from the revision subjects: a revision whose scope names no capability, or whose release-note words are unhelpful, produces an unclear entry or none at all. | Medium | Medium | The visibility refusal catches a version that would say nothing, but it cannot make a badly worded subject good; the maintainer's discipline in the commit message remains the upstream input. |
| R-018 | Every Cargo dependency update is announced, including build- and test-only crates, because `Cargo.lock` is a user-receiving path; a dependency release can therefore carry maintenance noise a crew member does not act on. | Medium | Low | Accepted deliberately: the Dependencies group sits last, and each entry states the crate and versions its revision carries. Excluding dev-only dependencies would need a different signal and is a separate decision. |
| R-019 | Users on Linux, macOS or any other platform have no distributed binary, and no CI target compiles those platforms after the release matrix narrows; the source-build route stated in the public text is unverified by the project. | Medium | Medium | Accepted deliberately: the public text states that other platforms are not supported or distributed, that their source can be built with a Rust toolchain, and that a platform may be added back when users request it. A returning platform arrives through a later change that adds its build-and-start evidence. |
| R-020 | Committing the applied state makes the project responsible for its secrecy and restorability, not just its correctness (ADR-0006 consequence; the state arrives with the mechanism chosen in ADR-0005). | Medium | High | Encryption is enforced for state and plan, the passphrase has no default and is never a repository secret, and the state is reviewed only for being ciphertext. |
| R-021 | The provider's object coverage and import identifier forms are version-specific, so an upgrade can change what a declaration can express or how an object is adopted (ADR-0005 consequence). | Medium | Medium | The concrete provider version is pinned in `infra/.terraform.lock.hcl`, the batch carries the identifier the pinned provider documents, and an upgrade is a reviewed change with the delta's scenarios re-run against a refreshed fixture set. |
| R-022 | Withdrawn CI drift reporting means configuration drift is found only when the maintainer runs the local check (ADR-0006 consequence). | Medium | Medium | Accepted deliberately for the passphrase boundary; the local check is the recorded control, and running it is part of the maintainer's routine rather than a scheduled job. |
| R-023 | Losing the state passphrase loses the applied state; the committed backup is protected by the same key (ADR-0006 consequence). | Low | High | The passphrase lives in the maintainer's password manager, and re-adoption rebuilds the state without changing anything live, so the loss costs time rather than correctness. |
| R-024 | There is no lock: two simultaneous adoptions or applies could race on the state (ADR-0006 consequence). | Low | Medium | The single-maintainer assumption is recorded; staging means a lost race leaves one complete batch, never a partial one. |
| R-025 | The committed state is public ciphertext: it can be read and modified by anyone, and only the passphrase protects its contents. | Low | Medium | Encryption at rest, review of the state as ciphertext, and the absence of any automation that holds the passphrase; integrity is re-checked by the refresh-only plan before a state is bound. |
| R-026 | Push protection may not be enableable on this free public repository: the pinned provider's own acceptance test for a public repository keeps it `disabled`, with a comment about purchased advanced security, while the live read reports the field and admin permission, GitHub's secret-scanning documentation states that secret scanning runs automatically for free on public repositories, and the push-protection page states it is disabled by default and can be enabled by a repository administrator, organization owner, security manager or enterprise owner (checked 2026-10-18). | Medium | High | A read-only preflight before the real apply confirms the live field and the admin permission and re-reads the documentation; the apply is still the proof. A refusal names the setting, changes nothing and **stops the change**; the question returns to the user rather than being papered over, and the operator's real apply after GREEN is required. |
| R-027 | The declaration's `security_and_analysis` block is provider-version-specific: 6.13.0 flattens only some of the statuses the API returns, its write path sends only advanced security, secret scanning and push protection, and `secret_scanning_validity_checks` is not even in its schema, so an upgrade can change which statuses a plan compares and the remaining checks cannot be declared at all. | Medium | Medium | The provider is pinned in `infra/.terraform.lock.hcl`; an upgrade is a reviewed change that re-runs the delta against a refreshed fixture set (R-021). A later change that wants non-provider patterns or validity checks needs a provider upgrade or another mechanism, not a declaration edit. |
| R-028 | The suite's write sandbox twins the API's shape, not its policy: it proves the preview names the change, the apply writes once and reports, but not that GitHub accepts both statuses on this repository. | Medium | High | The operator's real apply after GREEN is required evidence; the scenarios never claim to have proven live acceptance. |
| R-029 | A partial apply leaves a state that records the applied resources and not the failed one; committing it would record a revision that was not fully applied. | Low | High | The routine writes `terraform.tfstate.stale` beside the state and commits only a green apply's state; the next preview and apply refuse and name the stale state until a green apply records the whole revision and removes the marker. |
| R-030 | Private vulnerability reporting is off and cannot be declared by the pinned provider, so a manual change to it is invisible to the preview and the drift check. | Low | Medium | Recorded gap; the `SECURITY.md` reporting route remains the contributor path and the setting is checked by hand when the security surface is reviewed. |
| R-031 | A saved plan does not re-read the live configuration at apply time: a manual edit made between the preview and the preflight is refused, but an edit made *during* the preflight can still be overwritten. | Low | Medium | The routine runs a read-only `tofu plan -refresh-only -detailed-exitcode -json -target=<previewed objects>` immediately before `tofu apply` and refuses a non-no-op change by address; the JSON report is authoritative, not the exit status (opentofu/opentofu#3015), and an incomplete report refuses. A wrapper command that re-planned, compared and applied was rejected as a second apply path. |
| R-032 | The measurement's central premise is unverified: `cargo-bloat` 0.12.1 must read the symbol table of a `x86_64-pc-windows-gnu` PE built with `strip = false`. It reads PE symbols and falls back to a PDB only when the symbol list is empty, and a GNU-built PE has no PDB, so a PE it cannot parse yields no symbols at all; the generator is also old (last published 2024), so a future Rust/PE layout may break it. Its numbers are estimates of the `.text` section rather than a byte-exact accounting of the file. | Medium | High | The first implementation task is a spike that cross-builds the fixture and runs both `cargo bloat` JSON modes, recording the JSON keys; if the fixture yields no symbols it gains `-C link-dead-code`, and if the real project executable still yields none the change stops and the generator is re-decided with the operator. The pin makes the generator's version part of every report; a build it cannot read makes the measurement refuse and name the cause instead of printing a number, the totals are never substituted for the file size, and a bump is a deliberate change that re-records the version (the `git-cliff` and `cargo-about` pins are the same rule). |
| R-033 | The executable a measurement describes is named by its caller: the gate passes the artifact its own job built at the same revision, but a supplied artifact's origin is a claim, and on a pull request the measured revision is the merge revision rather than the branch head. | Low | Medium | The report records the artifact's source (`built`/`supplied`), digest and size beside the revision it names, so a mismatch is visible; the gate never supplies an artifact from another job or revision, and pull-request runs are compared with pull-request runs. |
| R-034 | The measurement is evidence, not a gate, so a broken measurement is green and can be ignored: a `cargo-bloat` or toolchain regression publishes an `unreadable` report while the Windows smoke and the release path continue, and nothing refuses the revision. | Medium | Medium | The report (or a note that none was written) is always appended to the step summary and the `size-attribution/` artifact is uploaded with `if: always()`, and the build-configuration reviewer reads the report while reviewing a revision. A hard gate was rejected because it would block Windows execution evidence and a tagged release on a generator regression; the report is the evidence and the review is the control. |

## Technical debt

| ID | Item | Impact | Plan to address |
|---|---|---|---|
| TD-001 | Fixtures and golden calendars are generated, so the support claim rests on generated layouts rather than observed producer variation. | A producer layout variation could fail in the field. | Local (uncommitted) validation against real plans; expand generated variations when evidence appears; a real second/third corpus is gated on documented permission (Q5). |
| TD-002 | The user's first draft oracle had five overlong lines, an incorrect future weekday, and untraceable values. | Copying it verbatim would encode contradictory evidence. | The golden calendars are regenerated in this change. |
| TD-003 | Private-source validation cannot be committed. | Reproducibility of real-source checks is manual. | Keep real plans local/ignored; rely on generated fixtures for committed evidence. |
| TD-004 | `archunit` and `pdfplumber` are pre-1.0 pinned dependencies. | Upstream minor releases may break the pinned API. | Pin exactly; Dependabot ignores their minor/major updates (deliberate bumps). |
| TD-005 | The actions and tooling in the release path (and the CI lint image) are pinned by mutable tags and branches rather than commit SHAs, including the third-party `dtolnay/rust-toolchain@stable` and `anchore/sbom-action@v0`. | A moved tag or branch could inject code into the release path; the stronger reference is not yet used. | Adopt commit-SHA pins repository-wide in one change, with Dependabot updating them (R-011). |
| TD-006 | **Closed 2026-10-17**: the macOS archives are unsigned; the one-time download approval is documented instead of signing and notarising. No macOS archive is published after this change, so there is no new signing or notarising work. | Closed for future releases. The already-published macOS assets stay as released and are not re-signed or withdrawn. | No action; a macOS archive returning would reopen the signing question in its own change. |
| TD-007 | The conversion reader's defensive arms carry fifteen uncovered lines: guards for input the supported family cannot print (a missing date band, an out-of-range footer date or zone, the compact-date conversions), the exhaustive-match arms of the `date()` accessor, the two hard-to-reach filesystem arms, the sink's raw newline and carriage return, and the unparsable construction-clock fall-through. | A variation of the source family could reach one of those arms unobserved. | A conversion change that hunts them: extend the fixtures that can reach an arm, delete the arms that cannot be reached, and re-measure. Recorded rather than closed here, because this change adds no production line in the conversion crates — the measurement moved from 880 instrumented and 865 covered lines to 889 and 874, i.e. by exactly this change's own step-definition lines. |
| TD-008 | (partly closed 2026-10-14 by the change to list only the changes a user receives) A version's notes are only as clear as the released revisions' own subjects. `Read the producer's own export layout` is a real parser fix a crew member could act on, but the words are the project's, not theirs, and no rule decides that — the machinery skip list and the user-receiving path list both judge *what* a revision touched, and neither can judge whether the words that state it are usable. The path list also decides by a maintained judgement: a change that reaches a downloader through a path nobody listed is not announced. | A reader can still be handed an entry whose words they cannot act on, and, in the other direction, a user-receiving change that came through an unlisted path is missing from the notes. | Commit subjects for released revisions written in a crew member's vocabulary, which stays the maintainer's authorship, and adding a path to the marked list whenever a change reaches a downloader through one the list does not name. Recorded rather than closed: the input is authoring discipline upstream of every rule this project owns. |
| TD-009 | (closed 2026-10-17 by the publication gate) The publish job refused only check runs that had already concluded non-green, so a check still in progress when the tag was pushed was neither green nor refused and publication did not wait for it. | Closed: a check that would have failed can no longer conclude after the release is public. Publication waits for every check outside the release-workflow suites, refuses a concluded non-success, no success, no evidence, an unreadable source, or the bound, and publishes only when every remaining check has concluded green. | Residual: the live API and the job ordering are proven only on the host (the operator boundary of 2026-10-13), and the commit check-runs endpoint returns at most the 1000 most recent suites; the gate fails closed. |
| TD-010 | Travel fragments pair only when both printed fields are equal — the crew position and the flight number — where the previous code suppressed the position on a positioning leg and so tolerated a partner printing none. | An unobserved variant of the source family, a split leg printing its crew position on one row only, is refused rather than converted. | Accepted deliberately: matching by flight number alone is ambiguous when a printed identification repeats, so refusing is the safer reading, and the refusal is explicit and pinned by the scenario "A positioning departure fragment has no partner when its arrival fragment prints no crew position". The local-corpus check covers the observed plans. |
| TD-011 | The dependency parser matches only Dependabot's `chore(deps):` prefix; a customized commit-message prefix, or a scope such as `chore(deps-dev):`, is silently unannounced. | A dependency release can omit an update a maintainer expected to see. | The fixtures pin the confirmed prefix; review the parser when Dependabot's commit-message configuration changes, and widen the prefix as a separate change (R-018 names the noise trade-off). |
| TD-012 | (closed 2026-10-17 by the regression fix) The empty-group prune matched a following version heading (`^## `) or the section end, not a following group heading (`### `), so an emptied non-final group kept its heading. The scenario "An emptied group before Dependencies is not listed" reproduced it with a filtered `feat` before a dependency update. | Closed: the prune now matches any following heading (`^##`), and the scenario pins the non-final empty group. | No further action; a future group can be added below Dependencies without leaking an empty heading. |
| TD-013 | The two Dependabot settings are bound by a second adoption batch that the operator must run before the preview. Skipping it is now refused: the preview's own plan JSON shows a `create` for a setting that already exists live and is unbound, and the guard names it before any write. The off-routine raw apply in that skip state still reaches the same live state because the enables are idempotent, and it is what the partial-failure scenario drives. | An operator who skips the adoption is stopped with the setting named, not shown a preview that claims to create something that exists. | The second batch is a named step in the apply routine (design.md, "The apply procedure"); the preview guard enforces the adoption rule, and a combined batch command is deliberately not introduced while each change owns its own pending batch. |
| TD-014 | The measurement attributes the workspace's single binary, and the human report lists the largest 25 functions of N while the machine-readable report holds every symbol. | A second workspace binary would make the generator's target ambiguous, and a reader who needs a small function must open the JSON. | Choose the binary explicitly when a second one appears; the JSON (or a larger limit) is the complete view meanwhile. |
