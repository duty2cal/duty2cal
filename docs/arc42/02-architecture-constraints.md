# 2. Architecture Constraints

> **Test-scope amendment (reduce-test-runtime).** The operational capability
> feature files remain as `@documentation`; their cucumber step definitions were
> deleted. Where this chapter names a scenario, a suite or a fake-API proof for
> an operational behaviour, the executable evidence is the owning workflow, the
> `bats` tests, or the maintainer's preview/apply. `scripts/setup-infra-tests.sh`
> covers only the provider/import/base setup. The product scenario suite is the
> conversion capability only.

## Technical constraints

| Constraint | Motivation |
|---|---|
| Rust, edition 2021, `stable` toolchain (`rust-toolchain.toml`) | Supplied constraint. |
| Cargo workspace with a crate boundary only where dependencies, target platform, or `crate-type` differ | ADR-0002 (reduced two-crate core + PDF split). |
| `pdfplumber = "=0.4.1"` (Apache-2.0), depended on only by `duty2cal-pdf` | Supplied exact pin, updated by the operator's brief; re-proved to build. |
| Hand-written RFC 5545 serializer with no calendar library dependency, in either the product or the tests; the golden scenario compares the published file | Output must be deterministic for the golden scenario, and the serializer carries no third-party licence obligation. |
| No native C/C++ dependency; core is `wasm32`-safe and does no I/O, clock or environment access | `crates/duty2cal-core/clippy.toml` `disallowed-types`/`disallowed-methods`, enforced by `cargo clippy --workspace -- -D warnings`. |
| Windows GNU target (`x86_64-pc-windows-gnu`), cross-compiled on Linux/CI, statically linked | Supplied distribution constraint (kept). |
| One self-contained executable, no companion DLL or runtime installer | Supplied distribution constraint. |
| `archunit = "=0.0.2"` architecture tests for the intra-crate layer direction | ADR-0002, level 3. |
| Typed errors (`thiserror`); no `unwrap()`/`expect()` outside test code | Operator brief conventions. |
| No network I/O at runtime | The converter is local and offline. The browser page makes no request to another origin after it loads and loads no third-party asset. |
| Browser target and facade: `wasm32-unknown-unknown`; `ffi/wasm` (`duty2cal-wasm`) is a bytes-in/result-out driving adapter with no filesystem, network or environment access; `getrandom` uses the `wasm_js` feature | The same application boundary serves the browser; the core remains free of I/O. `wasm-bindgen`, `js-sys` and `getrandom` are target-scoped under `cfg(target_arch = "wasm32")`, so native and Windows workspace builds stay free of wasm-only crates. |
| Browser page boundaries: inline WASM under `default-src 'self'; connect-src 'none'; script-src 'self' 'wasm-unsafe-eval'`, no persistent storage, no navigable URL or history entry, browser-owned save, a 20 MiB input bound, and a capability gate for WebAssembly and ES modules | The page's privacy promise must be structural, not asserted: the CSP forbids requests, the page uses no storage API, and the plan never leaves the tab. The inline bundle is required because `connect-src 'none'` blocks the loader's default `.wasm` fetch. A missing capability or a startup failure is refused by name and offers no picker. |
| The browser test supply chain is test-only and pinned: Playwright and `@axe-core/playwright` in `web/e2e/package-lock.json`, Node in `web/e2e/.nvmrc` after one LTS resolution, Chromium through the Playwright package, `wasm-pack` in `web/.wasm-pack-version` | Reproducible browser evidence without a runtime third-party asset; the pinned Node and browser driver keep the test surface from floating. A setup without them must fail loudly, not skip. |
| `duty2cal-wasm` is excluded from the native Cobertura denominator; the shared core stays covered through the CLI scenarios and the facade is browser-evidenced | The `wasm32` target has no file-based LLVM profile writer in this toolchain. The exclusion is an operator-approved coverage boundary, revisited only when wasm profiling becomes collectable; no native duplicate of the browser scenario is added. |
| The Public website is published from the monorepo into `duty2cal/duty2cal.github.io` by the write-enabled deploy key created by the declared configuration; the Pages repository holds only the Site output and is never edited by hand | One source and one publish path: the short canonical address is the page, and a hand edit in the target is removed by the next publication instead of becoming a second source. The credential is a prerequisite, not this path's output. |
| The Site output is one assembled directory (`dist/site/`) holding the page, the header's vector mark and its raster tab alternate, its script, the capability gate, the stylesheet, the WASM bundle, the licence file and the stamped footer, and nothing else; the exact member set is enumerated in chapter 7 | One artifact is gated, inspected and published, so the published bytes are exactly the bytes the gate approved; the source tree keeps source-only content and the footer is stamped without dirtying a source file. |
| The publication replaces the target's content in one commit pushed by fast-forward, under an exclusive lock; the pages rule set forbids non-fast-forward pushes, branch deletion and merge commits | The rule set admits the deploy key but not a force push, so a whole-content replacement must be an ordinary commit; the lock and the reusable workflow's concurrency group keep two publications from racing into a rejected push, and every earlier page stays in the target's history. |
| One reusable GitHub workflow, `.github/workflows/site.yml` (`on: workflow_call`, inputs `revision` and `since`, secret `PAGES_DEPLOY_KEY`), is the only host-side implementation of the publication: it prepares the toolchain, writes the key to a `600` file and runs `scripts/publish-site.sh`. `web.yml` is a trigger workflow (default-branch push and manual dispatch, no `v*` tag trigger) that calls it; `release.yml` has a `site` job that calls it for the tag and a `publish` job (`needs: site`) that publishes the archive. Both callers check out with `fetch-depth: 0`. | One host-side copy of one implementation: the trigger workflows hold no build or gate logic, the deploy key is materialised in exactly one place, and the tag's site publication is the same call the default branch makes. Removing the tag trigger from `web.yml` leaves exactly one owner for a tag's site publication — the release's `site` job — so one tag builds and gates one site. |
| The Site publication is one command whose evidence runs inside it as real subprocess checks, in fail-fast order: page content, licensing/REUSE, the browser check (every request after load) and the conversion suite (the export capability's non-browser, non-nested-build scenarios); the checks and the build run inside a detached `git worktree` at the publication revision, and the worktree borrows the checkout's installed `web/e2e/node_modules` by symlink only when the two `web/e2e/package-lock.json` files are identical, refusing by name and naming `npm ci --prefix web/e2e` otherwise | The refusal the use case promises must be executable and name the failing check, and the evidence must be that revision's own, not the caller's working tree's; the tag exclusion is what keeps the gate from re-entering the publication it is gating, and the lockfile comparison keeps one installed driver from silently standing in for the revision's pins. A gate held only in workflow text could neither run on a workstation nor be observed by a scenario. |
| The footer's Built revision is resolved at build time with `git describe` and `git rev-parse` from a detached worktree at that revision; the publication refuses an unresolvable revision, and an unclean caller tree is detected by `git status --porcelain --untracked-files=no` rather than a `-dirty` suffix | A published page may not name a revision that did not build it, the `tag-N-gSHA` form is produced by git rather than by the page, and describe does not append `-dirty` when a revision is named explicitly. The untracked-files exclusion is deliberate: an untracked build output or scratch file cannot enter the commit, because the commit's tree is the Site output, so only changes to tracked files make the published tree differ from the revision. |
| The Site publication's trigger decision is the command's `--since` argument: the command owns the site-input path list (`crates/**`, `ffi/wasm/**`, `web/**`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `LICENSES/MPL-2.0.txt`, `docs/assets/**`, `.github/workflows/web.yml`, `.github/workflows/site.yml`, the publication scripts `scripts/build-web.sh`, `scripts/build-site.sh`, `scripts/check-site-content.sh`, `scripts/site-evidence.sh`, `scripts/publish-site.sh`, and `run-tests.sh`), reports "no site input changed" and writes nothing; a `v*` tag publication omits `--since` and always builds | One owner for one rule: the trigger workflow keeps no `paths:` filter, so the "no publication on an unrelated revision" promise is a subprocess behaviour the bats tests prove instead of host-only configuration nobody can run. The accepted cost is a job start per default-branch push that may exit after the comparison. |
| Republishing a revision whose Site output the hosting target already holds reports that the target is current and exits 0 without a commit; the target's branch tip and the output are compared before anything is written | A retried or repeated publish is a no-op rather than an empty commit, so the target's history names one commit per distinct page and a re-run cannot look like a new publication. |
| The publication verifies the served page before it reports success: after the replacement and the read-back, the required `--verify-url` address is fetched with bounded retries, and the publication refuses unless the served page carries the same Built revision text as the output, naming the address and the served revision. It runs after the replacement, so a refusal cannot restore the previous page | The published promise is about the page a visitor receives, so a push that the host never serves must not be reported as a publication; the bounded retries tolerate normal Pages propagation without hiding a page that serves another revision, and the refusal's position makes a serving failure a fact the maintainer reads rather than a silent success. |
| A release is published only after the Site publication for its tagged revision succeeded and the hosting target's branch tip carries that tagged Built revision; the release's `site` job calls the reusable site workflow, and `scripts/publish-release.sh` in the `publish` job (`needs: site`) reads the target's branch tip with `git ls-remote` and a fetch, refuses before any `gh` call when it does not carry the tagged Built revision, and excludes `release-notes.md` from its asset comparison | The coupling is one workflow job dependency plus one verification the release command owns, so a release never announces a page the target does not hold, a site failure publishes no archive, and the release's check is a command the tests drive with a local target rather than host-only YAML. |
| The site publication is no longer driven by cucumber; its early refusals are covered by `bats` tests that invoke `scripts/publish-site.sh` with bad arguments, an unknown base, or an unclean tree and assert the refusal before any build. The workflow's build, evidence, and deploy steps are the remaining gate | The shell refusals run without cargo, git worktree, or a network call; no test reaches GitHub, and a bad invocation never reaches a build. |
| Windows x86_64 is the only supported platform in the published-archive sense and the only target offered for download: `x86_64-pc-windows-gnu` | One executable for the one archive platform; no other archive is published and none is tested by the automation, while builds for other operating systems are available on request. The browser is a supported conversion route and offers no archive. Other platforms' source may be built with a Rust toolchain. |
| Linux (`ubuntu-latest`) remains the CI, coverage and local test host and the host that cross-builds the Windows executable; it is not a published platform | The product suite runs on Linux and the Windows executable is cross-built there. This is engineering context for the project's own build and evidence path, not a platform promise. |
| Release packaging is a Linux-only POSIX-shell script (`scripts/prepare-release.sh`) outside the workspace | Packaging is build tooling, not product behaviour; it adds no workspace member and stays off the coverage denominator. |
| CI validates the workflows with `rhysd/actionlint:1.7.12` and enforces DCO sign-off on pull requests (`scripts/dco-check.sh`) | The release path only fails on the host, so a schema/expression check precedes the push; sign-off is required without granting a third-party app repository access. |
| Every release archive carries a build provenance attestation and a bill of materials (`actions/attest@v4`, `anchore/sbom-action@v0`) | A downloader can trace the file in hand to the tagged revision and this project's automation. |
| `git-cliff` 2.14.2 pinned beside `cliff.toml` in the repository, installed in CI with `taiki-e/install-action@v2` (`tool: git-cliff@2.14.2`) | The change-log gate compares generated text byte for byte, so the generator's output shape is part of the contract; an unpinned tool would make the comparison meaningless, as the `cargo-about` 0.9.0 pin already records. |
| A `changelog` CI job refuses a committed `CHANGELOG.md` that differs from a fresh render of the released revision, naming the version whose section differs, and the release preparation runs the same check before it stages anything | The released version's notes are that file's newest section, so a stale committed change log would publish a claim the repository does not hold; and the publish job now waits for the tagged revision's check runs and refuses a concluded non-success or the bounded wait, while the preparation's own drift check remains an independent pre-publication check. |
| The default `cargo test` verifies the product only: `duty2cal-core` and `duty2cal-pdf` unit/property tests, the architecture tests, the golden calendar test, and the `export-duty-plan-calendar` cucumber scenarios. Operational feature files stay in `givn/specs` as documentation under a feature-level `@documentation` tag, and a change's delta for such a capability carries the same tag; the assembler skips both the same way, and their step definitions are deleted | `cargo test` must not spawn `cargo`, `git worktree`, a cross-build, or a network call. Operational guarantees belong to the workflow that owns them, where they are cheap and real; re-binding an operational feature needs an ADR naming the defect no other mechanism catches. |
| The browser smoke is one `@e2e` scenario tagged `@browser`, excluded from the default run and exercised by a dedicated per-push CI job after the bundle and Site output are built; the remaining browser variants run per push only with `./run-tests.sh --browser`, and the nightly workflow runs all 16 | The default suite stays Rust-only; the rendered page still has a real Playwright proof without putting Node and Chromium on every local run, and the nightly gives the variants a scheduled signal. |
| The `test` CI job has a Rust cache, a 20-minute timeout, and no `mingw-w64`, `cargo-bloat`, `git-cliff`, OpenTofu, or browser toolchain; `run-tests.sh` prints `phase=<name> seconds=<n>` and the cucumber concurrency | The job's runtime is an owned quality requirement, not an accident; a phase line shows which class regressed, and a run over the timeout is a defect. |
| A nightly workflow (`.github/workflows/nightly.yml`, 03:17 UTC and manual dispatch) runs the product suite (which includes the CLI e2e), all 16 browser variants and `cargo deny check`; it holds `contents: read` and no state passphrase, administer token or deploy key. GitHub disables the schedule after 60 days without repository activity; a manual dispatch or any push re-enables it | The 15 non-smoke browser variants are on demand per push; the nightly makes them a scheduled signal without putting Playwright on every push. The disable rule is recorded in R-071. Configuration preview/apply and publication stay with the maintainer and the tag/default-branch workflows (ADR-0006). |
| The Windows cross-build job enforces a 2,097,152-byte budget with `stat` on the cross-built executable | A silent doubling is a red job. The ceiling is the last published executable's file size; a local cross-build of this revision measured 2,013,696 B. It is tightened only with a fresh measurement. |
| The site publication's full behavioural scenarios are no longer cucumber tests; its early refusals are covered by `bats` tests in a `scripts` CI job, and the publication workflow itself is the executable gate (golden test, build, evidence, deploy) | The publication's shell logic is tested without a cargo build or a git worktree inside `cargo test`; the workflow refuses before any deploy when a check fails. |
| The applied state's drift check is `scripts/check-drift.sh`, run by the maintainer with the passphrase and a read-only token in their own environment; no CI job holds either | ADR-0006 and the state-secrecy constraint stay in force. A CI drift job would put the means to decrypt the pages publishing key in a workflow. |
| A size attribution of the distributed executable is produced for every pushed revision by the `windows-gnu-build` job and uploaded beside the run; the `test` and `coverage` jobs no longer install the pinned `cargo-bloat` 0.12.1, and the budget is a separate gate | The generator belongs to the job that uses it; the per-push attribution remains the evidence a size lever is reviewed against, and the byte budget catches growth even when no one reads the report. The attribution's total — the `.text` size of the build that retains the names — is not the executable's file size. |
| The release profile carries `panic = "abort"` as a measured lever: 2,014,208 B against a 2,098,176 B rebuild of the unchanged configuration (saves 83,968 B on the release branch), with the failure outcome recorded | The reduction is measured and its consequence is explicit; a panic aborts with the standard Rust panic message, while a typed conversion failure still writes the numbered diagnostic. `opt-level = "s"` measured larger and is not applied. |
| The capability allow-list — which capability scopes are released changes — is the set of use-case ids present as directories under `givn/specs/`, materialised in `cliff.toml` and checked against the corpus by the renderer | `fix(ci)` is shaped exactly like `fix(publish-public-release)`, so the corpus, not the subject's shape, is the source of truth for what a capability is; a dependency update (`chore(deps): …`) is released without a capability scope through its own parser, below this allow-list. |
| A marked machinery skip list in `cliff.toml` — distinctive tooling phrases (`coverage report`, `ci workflow`, `e2e transcript`, …), realized as subject-anchored `skip` parsers and read by the renderer, which refuses a term the configuration does not realize | A `fix(<capability>):` revision that only reports on a coverage report, a CI or release workflow or an e2e transcript is not a change a reader can act on, and the type-plus-scope allow-list cannot see that; each term is a phrase rather than a bare word, and matching the subject only keeps a body that discusses the tooling from silencing a released change or a subject that merely borrows the word for a crew member's own work. |
| A marked list of the paths a user receives — the converter's crates and application, the browser page and facade (`web/`, `ffi/wasm/`), the build inputs that decide what the executable contains, and the packaging and release workflow that decide what an archive holds — read by the renderer, which refuses a listed path the tree does not hold | The allow-list and the phrase list both judge a revision by its words, and a subject written in the project's own vocabulary is invisible to a reader; a revision whose change touched none of these paths is left out of the notes whatever its subject says, and the list is a maintained contract: a change that does reach a downloader or a reader but not through these paths is announceable by adding the path. |
| The change log is rendered by a Linux-only POSIX-shell script (`scripts/render-changelog.sh`) outside the workspace | Rendering is build tooling, not product behaviour; it adds no workspace member and stays off the coverage denominator, like `scripts/prepare-release.sh`. |
| The public home's configuration is declared with OpenTofu (`required_version = ">= 1.7"`) and the `integrations/github` provider (constraint `~> 6.0`, concrete version pinned in `infra/.terraform.lock.hcl`) under `infra/` | ADR-0005. The floor is the version the state-encryption decision requires; the project pins the tool it runs in `infra/.opentofu-version` (`1.13.1` at this change) so the local planning commands and CI install a reviewed version, while a user's newer OpenTofu still satisfies the declaration's floor. The provider's concrete version is resolved into the lock file at setup. |
| The organization profile content and the organization's default security policy are sourced from `org/` and published by `infra/org_profile.tf`; the profile page itself is rendered by GitHub, not by the project | The public copy is reviewed and licensed in the same history as the code, and the profile repository is output. The project does not own that rendered screen, so the profile capability's executable evidence is the declared configuration and the maintainer's preview/apply, not a product test. The converter's own page is a project-owned browser-rendered screen and is driven by Playwright in the browser scenarios. |
| The profile repository is public and carries no declared scanning settings; its scanning state is GitHub's computed public-repository default | A public repository's scanning cannot be supplied as a distinct claim; declaring it would be a false value. The Pages repository already follows the same rule. |
| The profile declaration resolves its reviewed source through `variable "org_source_dir"` (default `../org` beside `infra/`); the adoption command stages the declaration without `org_profile.tf`, and the setup proof and security base workspaces omit it | The same declaration is planned from `infra/`, an adoption staging copy and test workspaces; a `file()` path that assumes one shape fails the others. The profile repository is created, never adopted, so no adoption or base workspace evaluates the profile files. |
| Pinned repositories have no declared object: the pinned provider exposes no resource, so pinning is a recorded one-time manual operator step; private vulnerability reporting is likewise a manual prerequisite | No second write path is introduced for a web-interface-only setting; the limitations are recorded in chapter 7 and as risks in chapter 11. |
| Public profile content embeds no image, badge, statistics widget or other third-party resource, and every link is absolute; it links the stable latest-release address and the source and site repositories, and attributes the third-party Unicode data to Unicode-3.0 | The profile must not contradict the converter's no-network promise by issuing third-party requests when the page is opened; relative paths are unreliable in the organization-overview context; the stable `/releases/latest` address does not rot, and the Unicode attribution completes the licence statement. |
| New public profile content names no third-party duty-plan provider or airline and states that the project is not affiliated with any; existing repository documents that already mention the provider were not edited by the archived profile change | The owner excludes the name for naming-rights reasons; the disclaimer states the absence of a relationship. |
| The applied state is local, encrypted at rest by OpenTofu's `encryption` block (PBKDF2-derived key over AES-GCM; `state` and `plan` both `enforced = true`) and committed as `infra/terraform.tfstate` with its backup | ADR-0006. Committing the state is acceptable only because plaintext cannot be written; `infra/.terraform/` stays ignored. |
| The state passphrase (`TF_VAR_state_passphrase`, at least 16 characters) and the administer token (`GITHUB_TOKEN`) exist only in the maintainer's environment: no default, no repository secret, no workflow | A default or a stored secret would defeat the encryption and put the administer credential in the repository it administers. |
| No `tofu apply` (or `init`/`plan` against the real organization) runs in GitHub Actions, and no configuration drift job runs in CI; the local check is `scripts/check-drift.sh` | The passphrase that could run a drift report would also decrypt the future publishing key; the drift check is local (ADR-0006), and the script makes the local control reproducible. |
| No locking; one maintainer applies at a time | A local backend with one writer; the assumption is recorded rather than enforced by a committed lock file. |
| The monorepo's security settings are declared in `infra/`: `security_and_analysis` supplies secret scanning and push protection, and the two Dependabot settings use their own resources; no `advanced_security` is supplied for a public repository | The public repository's credential surface is closed by the reviewed configuration rather than a settings page, and advanced security cannot be supplied for a public repository — declaring it would be a false claim. |
| The pages publishing credential is generated inside the declaration: an Ed25519 key pair from `hashicorp/tls` (`~> 4.0`, concrete version pinned in the lock file), the public half registered as a write-enabled deploy key titled `duty2cal.github.io publish` on `duty2cal/duty2cal.github.io`, the private half stored as the monorepo's `PAGES_DEPLOY_KEY` secret through the GitHub provider's sealed-box encryption | One credential pair, created by the reviewed plan rather than by hand, and no plaintext copy outside the passphrase-encrypted state and plan; the provider encrypts the secret value, so no libsodium or second tool is involved. |
| The organization's deploy-key policy is a manual prerequisite: `deploy_keys_enabled_for_repositories` must be `true`, and the pinned provider 6.13.0 has no attribute for it. It was confirmed before the archived pages apply and is true now | The organization can disable deploy keys for every repository and the declaration cannot express the setting. A disabled policy fails a credential create with 422 after the TLS key and rule set have landed, so the operator confirms it before any re-creation (chapter 7); chapter 11 R-056 records the gap. |
| The private key exists only in the encrypted applied state (and the encrypted, deleted-after-use plan): `tls_private_key` has no remote object, GitHub never returns a deploy key's private material, and the secret's `value` is sensitive but stored in state | Losing the passphrase loses the material behind the live deploy key; recovering it means replacing the live credential, which is a rotation decision (Q11), not a re-adoption. |
| The pages repository's protection rule set carries deletion, non-fast-forward and linear-history rules and names a `DeployKey` bypass actor with `bypass_mode = "always"` and no `actor_id` | The only writer is the publishing deploy key; a rule set that could block it would break publishing, and an unprotected default branch could be force-pushed or deleted. The bypass is by actor type, so any write-enabled deploy key on the repository bypasses the rules — the accepted cost of the user's decision (proposal D1). |
| The create-only revision runs a read-only creation guard before the preview and again immediately before the saved plan is applied: the deploy-key list, the Actions-secret list and the rule-set list are read with `gh api` and `jq`; a live object the revision would create and the state does not bind refuses, naming the address | The plan JSON cannot see an unmanaged live object, because a `create` resource is never read during plan; the guard is what keeps the adoption rule true for creates. |
| After a green apply the routine reads the applied state and the three live objects back; a failed read keeps the applied state, writes `terraform.tfstate.stale` and names the unreadable object and the reason | The provider's secret create makes one timestamp read and ignores its failure, and the framework performs no post-create read, so the routine is what detects an unreadable object after the writes. |
| A failed apply is classified by a live re-read after the pre-apply state is restored; a live object the revision creates makes the outcome partial, reinstalls the failed state and writes `terraform.tfstate.stale`, which refuses the preview and the apply until the operator removes it after reading the report and the next green apply completes the revision | SDKv2 persists planned values for a failed create, so the failed state's bytes cannot distinguish a refusal from a write; only the live read can. |
| A configuration change is a saved plan applied unchanged from the maintainer's workstation behind a read-only refresh-only preflight, and the resulting state is committed only after a green apply; a partial state carries a stale marker, and the preview and the apply refuse while it exists | The applied revision must be exactly the previewed one, a live edit since the preview must be refused, and a partial outcome must never be recorded as applied (chapter 8, "Apply semantics"). |
| Adoption is read-only: `tofu import` and `tofu plan -refresh-only` issue no write request to GitHub, and the adoption command refuses a batch that would need one | The adoption contract's guarantee: no live object is created, modified or deleted. |
| The local planning proof (`scripts/setup-infra-tests.sh`) exercises the real `tofu` binary and the provider's import/refresh/base-apply shape against a locally served fake GitHub API; no test reaches `api.github.com`, and both providers (`integrations/github`, `hashicorp/tls`) are installed from a local mirror. The adoption command and each configuration change are exercised by the maintainer's real preview/apply | The local proof must run offline and must not touch the real organization; the fake is the digital twin of GitHub, and the second provider exists only because the publishing key pair is generated by the declaration. |

## Organisational constraints

| Constraint | Motivation |
|---|---|
| Licence: MPL-2.0 for the project's code (per-file weak copyleft, App-Store compatible), including `ffi/wasm/**`, `web/*.js`, `web/*.css`, `web/*.html` and `web/e2e/**`; CC0-1.0 for `org/**` public profile and security-policy prose, for any non-code asset under `web/assets/**` and for `docs/assets/**` (the project's vector mark `docs/assets/duty2cal.svg`, copied into the Site output as `icon.svg`, and the raster `docs/assets/duty2cal.png` it was traced from, copied as `icon.png`); the published page and profile attribute third-party Unicode data to Unicode-3.0 with an absolute link to `LICENSES/Unicode-3.0.txt` | ADR-0001 for the code; the `org/**` and `docs/assets/**` exceptions are content-licensing choices whose canonical home is `REUSE.toml` (the design records the implementation), not a new architectural boundary; the vector master adds no licensing decision because the existing `docs/assets/**` override already covers it, and the vector is derived from the CC0-1.0 raster; the published page keeps its statement of MPL-2.0 for the code, CC0-1.0 for the non-code assets and the Unicode-3.0 attribution; the Unicode attribution completes the public licence statement. |
| `deny.toml` allowlist; any GPL/LGPL/AGPL/SSPL third-party crate is a hard failure | Keeps the project embeddable in any host app. |
| Per-file SPDX header; `REUSE.toml` for binary/data files; `cargo-about` notices; DCO sign-off, no CLA | ADR-0001 obligations. |
| Private duty-plan PDFs are read for analysis but never committed; fixtures and golden calendars are generated/anonymised | Privacy. |
| Changes follow the givn workflow; `.feature` files are the executable specification | Specification and tests are one artifact. |
| Declared configuration values are chosen, not inherited: no value enters `infra/` merely because it is the provider's default, and an undecided field is omitted and named by the first preview | The public home's problem is configuration nobody chose; an omitted field is visible, a default is not. The exception is an Optional-only boolean, for which the provider sends `false` when omitted, so every repository feature boolean is stated explicitly instead of being left to that default. |
| Public repository at `duty2cal/duty2cal` | The project's public home and release channel; standard GitHub-hosted runners, attestations and secret scanning are free there. |
| Published releases are immutable; a version tag is never reused | A downloader's file and the provenance covering it must not be replaceable after publication. |
| DCO sign-off enforced on pull requests (`scripts/dco-check.sh`), no CLA | The project's contribution terms; a change without sign-off does not land. |
| Contributor routes published: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, and the issue and pull-request templates, plus the organization's default security policy in the profile repository | A contributor finds the contribution route, the sign-off, the conduct policy and the confidential reporting route without asking; a repository without its own `SECURITY.md` inherits the organization default. |
| No private material in public assets: push protection and secret scanning block credentials, the private-data guard blocks duty-plan data | A public repository adds a credential surface; private duty plans must never enter the public history or a public asset. |

## Conventions

| Convention | Motivation |
|---|---|
| Dependencies point inward; each adapter implements exactly one port with no business logic | ADR-0002. |
| Value objects are built only through validating `Result` constructors with no public fields; ports are traits in `application` and know no adapter type; every port is exercised through the real adapters rather than a test double | ADR-0002, level 4. |
| No path or file handle crosses the use-case boundary (input `&[u8]`, output `String`) | Keeps one use case callable from CLI, WASM and UniFFI. |
| Strict Gherkin execution (`.fail_on_skipped()`); one step-definition file per capability | Prevents false completion. |
| Browser scenarios drive the rendered page through a real Playwright/Chromium driver; variants of one action are regular scenarios and the action has exactly one `@e2e` scenario | The `.feature` file is the executable specification, and an HTTP/fetch substitute would not exercise the UI. |
| Diagrams in arc42/design are Mermaid | Rendered consistently. |
