## Branch walk

### Scope

The delta covers proposal bullet 1 (own printed window, station, title = printed code) and bullet 3 (no warning/report) for the representable row, bullet 4 (any other `SB_<letter>_CF` still warns) and bullet 6 (golden fixtures untouched). Two proposal bullets are **not** fully mirrored, and one is mirrored under a false premise.

- **Finding F1 (High) — the "unusable shift row" behaviour changes in a way the spec never asserts, and the design's reason for omitting it is wrong.** Proposal: "A row carrying one of the three codes that cannot supply a resolvable interval … is a conversion error exactly as for other recognized timed codes". Today an `SB_F_CF` row with **both** time cells blank reaches the fallback's all-day arm (`application/mod.rs:620-632`) and publishes an all-day activity plus a warning; after widening `AVAILABILITY_CODES` the same row reaches `row_interval` (`application/mod.rs:531-541`, `:692-705`), fails `resolve` on the empty cell (`:707-710`, `timing.rs:15`) and becomes a **conversion error — no calendar at all**. No delta or permanent scenario covers a recognized timed code with no printed times (`grep` over the permanent feature for `SB`/`SBX` returns only rows with windows). `design.md` "Decisions → Decides D4" says "a shift row with one printed endpoint is already a conversion error through today's fallback, so the observable outcome is identical whether or not the code is recognized and a scenario could not distinguish the two": that is true only for the *no calendar* outcome; the diagnostic text differs (today `a required activity could not be resolved: unrecognized activity code "SB_F_CF" with only one printed UTC endpoint`, `application/mod.rs:613-618`; after, `a required timing could not be resolved: the printed clock is not readable: ""`), and for the no-times row even the outcome differs (calendar published before, none after). The proposal's unusable-shape list ("one printed endpoint, or an interval that is not positive") also omits the no-times shape. `usecase.md` §Examples carries only the one-endpoint case, and its rules already imply the error for a recognized timed code, so the durable contract is fine; the executable spec is not.
- **Finding F2 (Medium) — proposal bullet 2 is only half covered.** "two `SB_F_CF` days are two activities, and a `FREE` day between them stays separate": the third delta scenario proves three *different* codes on consecutive dates produce three events, but no scenario has two rows of the same shift code, and no shift row is interrupted by `FREE`. The generic `SB` scenario proves the mechanism, so the risk is low, but the proposal sentence names the exact real-data shape (`SB_F_CF` on 2026-11-15 and 2026-11-16) and is unproven.
- **Finding F3 (Low) — the third scenario's redundancy.** "Three standby shift rows produce three separate availability events and no warning report" is not a pure subset of the outline (the outline uses one row per plan, so co-existence in one plan is a distinct invariant), but its two trailing warning steps re-assert the outline's outcome and the scenario text hides its dates/windows inside the step bodies, unlike the corpus style of "a supported duty plan with SB window 08:00 to 12:00 on …". Minimal fix: fold the proposal's same-code/FREE shape into this scenario and state the dates and windows in the Given; that keeps one multi-row behaviour and removes the redundancy rather than deleting the scenario.
- Everything else in the delta is exactly what the proposal asked for: no translation, no prefix rule, no `CF` interpretation, no new severity/report section, no other code touched. "Done" is otherwise unambiguous.

## Questions for the operator

Ranked; both are genuine product/evidence choices the codebase cannot settle. Everything else above is resolvable inside the change and was recorded as a finding instead.

### Q1 — What should a recognized shift row with **no** printed times do?

- **Context.** Recognition moves `SB_F_CF`/`SB_M_CF`/`SB_S_CF` onto the `Availability` path. That path requires a resolvable positive interval; today's fallback publishes an all-day activity plus a warning when both time cells are blank. So a plan containing an all-day shift row converts today and would fail after the change. The proposal's unusable-row list mentions "one printed endpoint, or an interval that is not positive" but not the blank-times shape, and the design asserts the two paths are observably identical (they are not). Nothing in the codebase can settle which contract the operator wants; the November plan does not exercise the case.
- **Question.** When a row printed as one of the three shift codes carries neither a start nor an end time, should the conversion fail as an unusable recognized timed code, or keep today's all-day fallback with a warning?
- **Options.**
  1. **Conversion error (recommended).** Consistent with "represented exactly like SB" and with the settled "unusable rows take the existing conversion-error path"; also consistent with the use-case timing rule that a recognized timed code must build a positive interval. Gain: one rule for SB, RE, SBX and the shifts; no invented all-day availability. Cost: a plan that used to publish now fails until the source is fixed, and the failure report's row entry uses the timing sentence rather than the unrecognized-code sentence. Example: `SB_F_CF` on a date with blank Start/End → no calendar, numbered failure report lists the row under `Errors:`, reason `a required timing could not be resolved: the printed clock is not readable: ""`.
  2. **Keep the all-day fallback plus warning for shift codes without times.** Gain: no previously-converting plan starts failing. Cost: the shift codes become "timed when times are printed, fallback when they are not", which contradicts the use-case rule and the meaning of "recognized"; the row would still be represented as `UnrecognizedActivity`. Example: the same row → one all-day event titled `SB_F_CF` plus one warning and a warning report.
  3. **Split: error for one printed endpoint, all-day fallback when both are blank.** Gain: exactly today's outcomes for the no-times shape while matching the recognized path for the one-endpoint shape. Cost: both of option 2's problems remain, plus a third behaviour to maintain and document. Example: blank/blank → all-day + warning; start only → conversion error.
- **Recommendation.** Option 1. It is the only option that keeps the settled semantics ("recognized exactly like SB", "unusable rows take the existing conversion-error path") and avoids a code whose representation silently depends on which cells are filled. It costs a new scenario (RED today: the all-day calendar is published) asserting no calendar, the row under `Errors:`, and the absence of the unrecognized-code sentence; and a one-line use-case example for the blank-times shape.

### Q2 — Must the reference generated plan print the three shift codes, or is a documentation split enough for the support evidence?

- **Context.** `docs/evidence/supported-duty-plan.md` is the evidence authority the support-statement check reads, and its §"What the fixture prints" now lists the three shift codes among accepted codes while no generated plan prints them (F15). The public support statement itself does not enumerate codes, and `scripts/support-statement-check.sh:152` only asserts that the record names the codes the fixture prints, so the choice is about what the record may claim as evidenced, not about a failing check.
- **Question.** For a newly recognized code, is evidence at the level of dedicated Gherkin scenarios (the delta) sufficient, or must the generated reference plan itself print the code so the committed golden calendar exercises it?
- **Options.**
  1. **Keep the generated plans unchanged; split the evidence record (recommended).** Move the three codes out of the "What the fixture prints" sentence into an explicit "codes the conversion accepts, exercised by the capability scenarios" statement. Gain: truthful record, no churn in `2026-06.ics`/`2098-06.ics`, no new golden review. Cost: the record can no longer be read as "the golden plan proves every accepted code"; a reader must follow the scenarios for the shift codes. Example: record says the generated plans print `… SB, SBX, RE, TK, DTUSA, EM …`, and a separate sentence lists the shift codes with the delta scenarios as their evidence.
  2. **Add the three codes to a generated plan and regenerate the committed expected calendar(s).** Gain: strongest evidence — the golden oracle itself would fail if the codes regress. Cost: new rows change `UID`s and event counts in a committed fixture, the change grows beyond "data plus docs", and the reference plan's 26-event narrative (and its browser equivalence twin) must be re-reviewed. Example: one `SB_F_CF` row 03:30-13:00 added to the June 2098 plan, with `2098-06.ics` regenerated.
- **Recommendation.** Option 1. The support statement's public claim does not enumerate codes, the delta scenarios exercise all three codes through the real CLI, and the record can be made truthful with a two-sentence split; option 2 buys stronger oracle coverage at the cost of rewriting a reviewed golden fixture and its evidence narrative, which this narrow slicing change does not need.

### 2. Is the named-run constraint real, and is the recorded reason exact?

Constraint: real. `run-tests.sh:185-195` — "A named run must select exactly one scenario", enforced as `if [ "$has_name" = 1 ] && [ "${total:-0}" -ne 1 ]` with "run-tests: the name selected N scenarios; exactly one is required" (`:194`). Mechanism: cucumber's `--name` is a regex over scenario names (`cucumber-0.23.0/src/cli.rs:93-99`), and outline expansion (`cucumber-0.23.0/src/feature.rs:98-230`) copies the scenario and only substitutes templates in its name and steps — no per-example index is appended to `expanded.name`. Every example of an outline whose title has no placeholder therefore has the identical name, one title regex selects all of them, and the named run is refused. So "an outline's examples are selected together" was exact for the outline this change had, and a single named run per example was impossible. Nuance if an outline is ever reconsidered: a title containing `<placeholders>` would yield distinct names and could be isolated per example, at the cost of splitting one behavioral claim across names.

Consequence for the final shape: the consolidated scenario is a plain scenario, and its title is unique in the assembled corpus (checked against `givn/specs/**` and `apps/cli/tests/**`), so `--name "<title>"` selects exactly one. `design.md:101` no longer carries the outline rationale because no outline remains; the constraint and its evidence are recorded here instead.
