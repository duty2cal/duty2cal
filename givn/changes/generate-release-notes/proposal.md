# Proposal: generate-release-notes

## Release note

> Record what each released version of the tool changed in a change log a reader can scan, group the released changes by kind, and refuse to publish a version whose notes say nothing a user can see.

## Use-Case Context

- Use-case ID: `publish-public-release` — "Publish a public release"; this change extends it rather than opening a second goal, because a release that states what changed is the same goal the use case already owns.
- Ideation topic: none. The change follows the operator's direction after the first release, and it has no seed.
- Seed path: none.
- Confirmed Personas:
  - `crew-member--personal-calendar-owner` — the person who reads a release's notes before deciding whether to download it; confirmed on 2026-10-10, promoted on 2026-10-12.
  - `project-maintainer--release-owner` — the person who writes the revision subjects the notes summarise, and who answers for the claim that a version changed something; same confirmation and promotion.
  - Neither Persona is a Gherkin Actor of this change.

## Problem / Opportunity

The first release demonstrates the gap. Its notes were generated from the release-note subjects of every revision it contained, which is the rule the publishing use case fixed — and the result was fifteen bullets of which two describe something a user can see:

```
# duty2cal 0.1.0

- Convert a supported Released Roster duty-plan PDF into one complete RFC 5545 calendar file…
- align the design with the implementation and correct the coverage merge
- build a clean merged coverage report
- … twelve more, ending with "put the MPL-2.0 text at the root so the project page states the licence"
```

Four things are missing rather than wrong.

- **No grouping.** A reader cannot tell a new capability from a build fix; the list is one flat sequence in revision order.
- **No filter for what a user can see.** The rule lists any revision whose subject carries a release-note type, so internal work typed `fix(...)` — a CI job, a coverage merge, a guard, the notices pin — reads exactly like a fix a user would care about. Nothing in the pipeline notices, because nothing checks that a release states a user-visible change at all.
- **No change log in the repository.** The notes exist only on the release page, so a reader who is reading the source sees no history of what changed between versions, and there is nothing to compare a version against.
- **No comparison to the previous version.** A downloader cannot tell what is new since the version they already have.

The opportunity is a change log the project generates from the same revision subjects it already stamps, groups by kind, filters to what a user can see, keeps in the repository, and refuses to publish empty.

## Proposed Solution

### What a released version's notes state

A version's notes name the changes a user can see, grouped by kind — new capabilities, fixes, performance, reversals — with the group a reader would look for first at the top. Each entry states the change in the release-note words the project already stamps on the revision, so the notes and the history agree.

Work that no user can see is not listed: housekeeping, documentation, test and tooling revisions, and the internal machinery of building, packaging and publishing. A revision whose subject names a capability is a released change; a revision whose subject names a tool, a workflow, a check or a document is not.

Where a version contains nothing a user can see, it is not releasable at all: the release refuses and says so, rather than publishing a version whose notes say nothing.

### The change log a reader keeps

The repository carries a change log whose newest section is the version being released and whose earlier sections stay as they were, so a reader can see what changed in any version they have, and what a version they are considering contains. The change log names each version with its date and links the comparison against the previous version.

The change log is generated by the project's own tooling from the repository's history, and a check refuses drift between the committed file and what the tooling would produce from the released revision — the same shape the third-party notices already use. The released version's own notes are the section of that change log, so the release page and the repository cannot disagree.

### How it is produced

- One generation step, driven by a configuration the project owns, that decides which revision subjects count, how they group, and what the rendered section looks like.
- The generator is a pinned version, recorded in the repository beside the configuration, so the same history renders the same change log — the gate compares generated text, and an unpinned tool would make the comparison meaningless.
- The change log is one of the files a release publishes, so a downloader can read it without visiting the repository.

### What the first version back-fills

The change log starts with the released `0.1.0` section, generated from the history under the new rules, so the corpus begins complete rather than at the next version. It will differ from what the release page says today — that page's list was generated by the older rule — and the change records the difference instead of editing the release.

### Release evidence

The claims above hold only with evidence: the generation is reproducible from a clean checkout (the committed file matches a fresh render), the grouping and filtering are exercised by the scenarios the specification will carry, the refusal of an empty release is demonstrated, and the first generated section for `0.1.0` is compared against the history it summarises.

## Out of Scope

- **How a version is released.** A pushed tag stays the only entry point, and a transient failure is repaired by re-running that workflow from the Actions tab; a failed revision is repaired by fixing forward to the next version. Decided by the operator on 2026-10-13, after the first release showed that a re-run cannot repair a fault in the workflow itself.
- **Pinning the workflows' actions to commit hashes.** The residual risk the publishing change recorded (R-011, TD-005) is real, and it is a supply-chain concern rather than a change-log one; it belongs in a follow-up change of its own.
- **Rewriting any published release.** `0.1.0`'s assets and tag are immutable; its page mentions the workaround for its archives, and its section of the change log is generated, not edited.
- **A hand-written highlights section** for a release. The notes stay generated, with the operator free to edit a published release's body as they always could.
- **Announcing releases elsewhere** — no changelog hosting, no feeds, no notifications.

## Open Questions

None remain open. Two decisions this change would otherwise have asked about are recorded here with the alternatives they rejected:

- **The release trigger** — tag push only, with a re-run for transient failures and fix-forward for faults. Rejected: a manual trigger that names a version and tags the revision it runs on, which would remove the hand-pushed tag and the tag move the first release needed, but adds an entry point the operator did not want. Source: the operator's decision of 2026-10-13.
- **Where the change log lives** — one file in the repository, generated and drift-checked, and published with the release. Rejected: notes only on the release page, which leaves a reader of the source with no history, and a hand-maintained file, which drifts from the history it claims to summarise.
