# Proposal: publish-site-plumbing

## Release note

The site repository now carries a write-enabled deploy key whose private half
is stored as the monorepo's publishing secret, and its default branch refuses
deletion, force pushes and merge commits from every writer except a
write-enabled deploy key, so the site can later be published from the monorepo
without a hand-made credential.

## Problem / Opportunity

The pages repository `duty2cal/duty2cal.github.io` serves the stock Jekyll site
and has no protection and no publishing credential. An authenticated read on
2026-10-19 confirms all three facts: the repository's rule-set list is empty,
its deploy-key list is empty, and the monorepo's Actions secret list is empty.
The repository is therefore writable by any actor with access, and the
monorepo holds nothing that could publish to it.

The website topic that follows needs both halves. It needs a write-enabled
deploy key registered on the pages repository, because that is the credential a
publishing workflow uses without holding a personal token. It needs the
matching private half stored where the workflow can read it, as the monorepo's
`PAGES_DEPLOY_KEY` secret. And it needs the pages repository's default branch
protected, because otherwise a mistake can force-push over or delete the only
copy of the published site.

Those three objects interact. The publish key is the only writer; a protection
rule set that requires pull requests or binds only to humans would either block
publishing or leave the repository unprotected. That is the fork the seed's
question Q2 records, and it is decided here rather than left to the website
topic, because the rule set and the key must be created together.

The opportunity is the same one the public-home topic exists for: a credential
and a protection rule that can be reviewed, diffed, previewed and rebuilt,
instead of a key generated by hand and two settings pages whose result nobody
can diff. The 2026-10-17 repository transfer is the realized cost of the
alternative — a manual change whose consequence was discovered afterwards.

## Proposed Solution

- **The declaration gains three objects.** The pages repository carries a
  write-enabled deploy key with a stated title; the monorepo stores the
  matching private half as the `PAGES_DEPLOY_KEY` secret; and the pages
  repository carries its own protection rule set for the default branch. The
  rule set forbids deletion, non-fast-forward pushes and merge commits, and
  names the deploy-key actor type as an actor that may always bypass those
  rules.
- **The preview names the creations.** A preview of the revised declaration
  names exactly the deploy key, the secret and the rule set as live objects to
  create; it also names the generated key material, which exists only inside
  the declaration's encrypted state and has no live counterpart. The preview
  writes nothing to GitHub.
- **A live object is never re-created.** If the pages repository already holds
  a deploy key with the declared title, or the monorepo already stores
  `PAGES_DEPLOY_KEY`, or the pages repository already holds the declared rule
  set, and the applied state does not bind it, the preview is refused and
  names the object. The owner must adopt it or remove it deliberately; this
  change offers no adoption batch for these objects.
- **The apply creates the three objects.** The previewed revision is applied
  unchanged: the key is registered, the secret is stored with the private half
  the provider seals with the repository's public key, and the rule set becomes
  active. The applied state records the three new bindings.
- **The stock site and its source are untouched.** The apply publishes no
  file, changes no Pages configuration, rebuilds nothing, and leaves the
  repository's `main` content alone. Nothing reads the credential until the
  website topic adds the workflow that uses it.
- **A partial outcome is stated honestly.** If the apply fails after the deploy
  key has been created, the outcome names the objects that exist and the one
  that failed, the applied state is marked stale beside itself, and the next
  preview refuses and names the stale state until a green apply records the
  whole revision.
- **The credential is dormant, and that is deliberate.** No workflow exists
  that consumes the key, so no scenario and no release claim depends on a
  publish succeeding; the website topic owns the first publish.

## Open Questions

### D1 — May the pages repository's protection rule set bypass the publish deploy key? (seed Q2)

- Question: the pages repository's only writer is the publishing deploy key
  created by this change. Should the rule set grant a bypass, restrict itself
  to rules that cannot block a push, or be omitted?
- Options:
  1. **Bypass write-enabled deploy keys; protect everything else.**
     Meaning: deletion, non-fast-forward and linear-history rules apply to
     every actor, and the ruleset names the deploy-key actor type as always
     able to bypass them. A `DeployKey` bypass actor carries no id — the pinned
     provider's schema says not to set one and GitHub ignores it — so the grant
     covers any write-enabled deploy key on the pages repository, not only the
     key this change creates.
     In practice: a human force push to the pages repository is refused and the
     publishing key's push succeeds; a second write-enabled deploy key added
     later would also succeed.
     Gain: the repository is protected against accidental human damage without
     breaking publishing, and a future blocking rule (a pull-request rule, for
     example) cannot silently break the publish path.
     Cost: the bypass covers an actor type rather than one key, so every
     write-enabled deploy key on the repository bypasses the rules; the
     declared key's own pushes are unreviewed by definition, and a compromise
     of it is not contained by the rule set.
  2. **Protect only what cannot block a push.**
     Meaning: the rule set forbids deletion and non-fast-forward pushes but
     imposes no actor bypass.
     In practice: a human cannot delete `main`, and the deploy key pushes as
     before, because none of the rules can block a push.
     Gain: simpler, with no bypass actor to maintain.
     Cost: nothing forces a review of a human change to the pages repository,
     and a later pull-request or required-check rule would break publishing
     unless someone remembers the exception.
  3. **No rule set on the pages repository.**
     Meaning: the pages repository keeps today's unprotected state.
     In practice: `main` can be force-pushed or deleted by any writer.
     Gain: nothing to configure or drift-check.
     Cost: a bad publish or a mistake destroys the only copy of the site.
- Disposition: **answered** — option 1, decided by the user on 2026-10-19 and
  confirmed again on 2026-10-19 after the actor-type constraint was disclosed.
  The pages repository's rule set carries deletion, non-fast-forward and
  linear-history rules, and names the `DeployKey` actor type as a bypass actor
  with `bypass_mode = "always"` and no `actor_id`; the provider says not to set
  an id for that actor type and GitHub ignores one, so the bypass is by actor
  type: any write-enabled deploy key on the pages repository may push. Rejected:
  option 2, because it leaves the repository without a review path for human
  changes and makes every future blocking rule a publishing hazard; and option
  3, because an unprotected default branch is the failure the public-home topic
  exists to prevent. The cost is accepted explicitly: the bypass covers every
  write-enabled deploy key, the declared key's own pushes are unreviewed, and
  the key's compromise is not contained by the rule set. Realized in
  `design.md` ("The declaration", "Decisions") and by the delta's rule-set
  scenario.

### D2 — Does a review gate the apply? (seed Q10)

- Question: should the apply refuse a revision the reviewer has not approved,
  record the review but let the owner apply anyway, or not model review in the
  apply flow at all?
- Options:
  1. **Gating: no approval, no apply** — gain: every applied change has a
     second reader; cost: a solo maintainer blocks on a second person, and the
     opening state (the reviewer is the owner) needs a bypass.
  2. **Advisory: review is recorded, the owner decides** — gain: no blocked
     solo workflow; cost: the reviewer cannot stop a change.
  3. **No review step in the apply flow** — gain: simplest flow; cost: an
     unreviewed revision can reach live configuration.
- Disposition: **out of scope** — this change is reviewed through the givn
  workflow and its operator applies the declaration after GREEN; no approval
  record, gate or bypass is built. The question stays open in the topic log
  (`givn/ideation/public-home-infrastructure/questions.md`, Q10) and is decided
  by a change that models review in the apply flow.

### D3 — What may an apply delete, and how are credentials rotated? (seed Q11)

- Question: which declared objects may an apply delete, and which must it
  refuse to delete; and does a key rotation remove the live credential or only
  stop managing it?
- Options:
  1. **Never delete a repository, the organization or a published release;
     allow lesser objects** — gain: the destructive class is bounded while
     ordinary cleanup works; cost: a repository can only be removed by hand.
  2. **Delete any declared object, with the preview naming every deletion** —
     gain: one rule; cost: a mistaken edit can destroy the public home.
  3. **Never delete; removal from the declaration only stops managing the
     object** — gain: the apply is non-destructive by construction; cost:
     cleanup is manual and the object stays in the drift report.
- Disposition: **out of scope** — this change creates objects and removes and
  rotates none; the use case's no-removal rule already excludes removal, so no
  scenario here deletes or disables anything. The question stays open in the
  topic log (Q11) and is decided before a change removes a declared object or
  rotates the publishing credential.
